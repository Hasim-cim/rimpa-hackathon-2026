Chapter 1 · Check

Citation check before filing

Before an AI-assisted document is filed, every reference is looked up. The result is attached to the record, so anyone later can see what was checked and what wasn't.

The tool never says "true" or "false". It reports what it found.

How it works

  1. Pull the reference list out of the draft.
  2. Look each one up in Crossref, then OpenAlex.
  3. Mark each as found, mismatch, not found, or not checked (things like legislation).
  4. Save the results as a check record linked to the document.

Build estimate 💭

1 hReference extraction (regex first, LLM if needed)
1 hCrossref and OpenAlex lookups with fuzzy title match
1 hResults screen and check-record export
3 hTotal. No API key needed for Crossref.

Risks

  • Citation checkers already exist, so on its own it is not novel. The records angle is filing the check with the document.
  • Legislation and grey literature are not in Crossref. We show them as "not checked" rather than pretend.
  • IM core is only medium. It checks before the record exists rather than managing the record.
Verdict. The safest build and the sharpest demo. Strongest as step one of a bigger product, and as our fallback if everything else slips.
Chapter 2 · Weigh

Evidence weight

Every statement in a document is traced back to the records it rests on. Whether AI or a person wrote it doesn't change the test. What matters is whether an authoritative record supports it.

Judging authenticity and reliability (ISO 15489) against authoritative records
Who uses it

Built on

Judge it speaks to

Record Check · Evidencemockup · click a sentence
supportedweakunsupportedcontradicted

Hardship assessment summary · case 2026/0412

How it works

  1. An LLM splits the text into separate claims. That is its only job.
  2. Fixed rules link each claim to records: same case number, same field, same date range.
  3. Each source is weighed: is it in the official system, current, created by someone with authority, reviewed?
  4. Claims get a colour. A person confirms any link before it is relied on.

Build estimate 💭

1 hSeed about 20 authoritative records for one case
1 hClaim splitting with one LLM call
1.5 hLinking rules and source weighting in SQLite
1 hHighlighted document and trace panel
4.5 hTotal. The riskiest of the five.

Risks

  • Claim splitting can go wrong. Keep the LLM out of the judgement and show its output for a person to check.
  • Never say "true". Say "supported by authoritative records". A record of a wrong decision is still a valid record.
  • The standards we'd build on (W3C PROV-O, ISO 23081, ICA's Records in Contexts) are not yet checked ⚠️.
  • Say "ontology" only when Christensen or Tolliday ask. Pitch the outcome.
Verdict. The most original idea and the best answer to "AI use isn't the test, evidence is". Keep it small: one case, about five entity types, rules not reasoning engines.

Build estimate 💭

How it works

  1. Mark a model and version as withdrawn or faulty from a date.
  2. The register returns every T1 to T3 record that model produced, highest tier first.
  3. A re-review queue opens. Every decision on it is logged.
  4. A targeted check of a few records instead of all of them, or none.

Build estimate 💭

0.5 hSeed about 40 past passports across 3 models
0.5 hRecall query and tier counts
0.5 hRecall screen and queue
1.5 hTotal

Risks

  • Only works if the model version was captured at the time, which is why it depends on the passport.
  • We haven't checked whether any product already does this (open question 5) ⚠️.
  • The data is seeded. Say so on stage.
Verdict. Our most novel claim, and the quickest to build. The best closing moment for a demo.
Chapter 5 · Authenticate

Record-of-issue check

A government intake system doesn't try to spot a forged stamp. It asks the issuing register whether this document was ever issued, and rejects it if not. That works however good the forgery is.

Records act
Authenticity, tested against the record of issue
Who uses it
Intake staff; information manager keeps the issue register
Brief angle
Disinformation: AI-forged documents
Built with
A seeded issue register and a lookup
Intake · Verify documentmockup · example data

How it works

  1. Read the reference number, issuer and date off the document.
  2. Look it up in the issuer's register of issued documents.
  3. Compare the details, and the file hash where one was taken at issue.
  4. Accept, reject, or send to a person. Log the check as a record.

Build estimate 💭

0.5 hSeed an issue register
1 hRead fields from an upload (OCR or LLM)
0.5 hLookup, compare and result screen
2 hTotal

Risks

  • Verification codes on certificates may already do this ⚠️. Check before Sunday.
  • The AI link is indirect. It defends against AI forgeries but doesn't manage AI-made records.
  • Only works for issuers who keep a register and share it.
Verdict. The simplest build with a sharp disinformation story. A standalone backup if the team prefers it, not part of the main product.

What it changes downstream

  1. Every check now ends in a filing gate: Ready to file, Needs attention, or Blocked, with the reasons against this type's bar.
  2. A Blocked document cannot be issued a passport until it is fixed or the IM changes the bar.
  3. The passport records the document type, the gate result and the policy version, so a later reviewer knows which rules applied.

Build estimate 💭

0.5 hPolicy file and four sector presets
0.5 hGate rules over the weights and citation statuses
1 hSetup forms and wiring into Check and Passport
2 hTotal

Risks

  • Presets are our generic starting points. Never present them as a regulator's rules.
  • The bar is thresholds over our own weights, so it is only as good as the linking rules under it.
  • A careless IM can set the bar to zero. The policy version on every passport makes that visible later.
Verdict. The piece that makes the information manager the author of the system rather than its auditor. Cheap, and it gives the demo a second "aha": change one number on the Setup page and the same document goes from Blocked to Ready.
Chapter 7 · Decide

What we'd build: Record Check

Chapters 1 to 4 are four steps of one workflow, not four products. Chapter 6 is the control panel over them. Chapter 5 stays separate as a backup.

Step 0 · ch 6Set the policyIM defines what good looks like
Step 1 · ch 1Check citationsfound, mismatch, not found
Step 2 · ch 2Weigh the evidenceeach claim traced to records
Step 3 · ch 3Issue the passporttier, model, sources, reviewer, hash
Step 4 · ch 4Recallfaulty model, records queued

Demo in three clicks

  1. The caseworker submits the summary. A fake citation and an unsupported human sentence both go red.
  2. They fix it, a reviewer signs off, and it's filed as T2 with its passport.
  3. "Six months later." Recall finds 14 records, 3 decision-informing.

The line: records management decides what to trust by evidence, not by whether AI touched it.
